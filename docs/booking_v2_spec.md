# Smart Booking V2 - System Specification (Powertech)

## 1) วิเคราะห์ปัญหาระบบเดิมและความต้องการใหม่
- ปัญหา:
  - สถานะการจองบนหน้าจอกับฐานข้อมูลไม่สอดคล้อง และรายการที่ยกเลิก/ถูกปฏิเสธยังไปแสดงใน Timeline/Calendar
  - UX ซับซ้อน หลายมุมมองทำให้ผู้ใช้ทั่วไปหาปุ่มจองยาก
  - ไม่มีการอัปเดตแบบเรียลไทม์ ผู้ใช้ต้องกดรีเฟรชเอง
  - การกรองหลายบริษัท (PTA/PT4/PTE) ยังไม่สม่ำเสมอในทุกหน้ามุมมอง
  - การแจ้งเตือนไม่ครอบคลุมทุกเหตุการณ์
- ความต้องการใหม่:
  - UX ที่เรียบง่าย: ปฏิทิน + จองด่วน + ค้นหาห้องว่างในหน้าเดียว
  - กรองบริษัทได้ทุกมุมมองและทุก API
  - อัปเดตข้อมูลแบบเรียลไทม์ (auto refresh/polling ที่เบาและเชื่อถือได้)
  - ป้องกันการชนเวลาจอง ตรวจสอบความว่างก่อนสร้าง
  - รายงานและสถิติ: สรุปจำนวนครั้งและเวลาการใช้งานต่อห้อง ต่อเดือน
  - แจ้งเตือนการสร้าง/แก้ไข/ยกเลิกให้ผู้เกี่ยวข้อง

## 2) ออกแบบระบบใหม่
- โครงสร้างข้อมูล:
  - bookings: รองรับฟิลด์รายละเอียดการประชุม, recurring (parent_id), สถานะ (Pending/Confirmed/Cancelled/Cancellation Requested/Rejected)
  - meeting_rooms: มี company, capacity, images, requires_approval, rate_per_minute
- Roles:
  - user: จอง/ดู/ยกเลิกคำขอของตน
  - staff/admin: อนุมัติ/ปฏิเสธ, แก้ไขรายการ, รายงาน
- UX หลัก (หน้า booking_v2):
  - Header: ปุ่มกลับ, เลือกบริษัท, ปุ่มสลับธีม
  - ซ้าย: ปฏิทิน FullCalendar (eventClick เปิดแก้ไข/ดูรายละเอียด)
  - ขวา: ค้นหาห้องว่าง (ช่วงเวลา), การจองของฉัน (เฉพาะวันนี้)
  - Modal จอง: ฟอร์มเรียบง่าย (title, start, end, agenda)
- API:
  - get_calendar_events: รับ start/end/company, กรองสถานะที่ไม่ต้องแสดง, ต่อกับ meeting_rooms เพื่อแสดงชื่อห้อง
  - search_available_rooms: ตรวจสอบความว่างระหว่างช่วงเวลา, exclude bookings ที่ชนเวลา
  - create_booking / update_booking / cancel_booking_request
  - get_bookings_by_date: กรองตามบริษัท
- Realtime:
  - ใช้ polling 10 วินาทีเพื่อรีเฟรช events และ “การจองของฉัน” เพื่อลดความซับซ้อนฝั่งเซิร์ฟเวอร์
  - อนาคต: เพิ่ม WebSocket โดยใช้ ws ที่มีอยู่ เพื่อ push updates เมื่อมีการเปลี่ยนแปลง
- การแสดงผล:
  - สีแตกต่างตามสถานะ (Confirmed=น้ำเงิน, Pending=ส้ม)
  - หลีกเลี่ยงการคิวข้อมูลที่ถูกยกเลิก/ปฏิเสธในปฏิทิน/รายงาน

## 3) คุณสมบัติหลัก
- หน้าจอการจองที่ใช้งานง่าย (booking_v2.html)
  - ปฏิทิน + จองด่วน + ค้นหาห้องว่างในหน้าเดียว
- ระบบจัดการการจองแบบใกล้เรียลไทม์
  - Polling รีเฟรชทุก 10 วินาทีในหน้า v2
- การแจ้งเตือน
  - Telegram ผ่านฟังก์ชัน sendTelegramNotification (อยู่ใน api.php)
  - SweetAlert บอกผลการทำรายการ
- รายงานและสถิติ
  - monthly_report.html และแท็บ “รายงาน” ใน booking.html (เวอร์ชันเดิม)
  - สามารถต่อยอดเพิ่มตารางสรุปเวลาใช้งานต่อห้อง/ต่อเดือน

## 4) แผนทดสอบ
- การใช้งานทั่วไป:
  - จองด้วยช่วงเวลามาตรฐาน 1 ชั่วโมง → เห็นในปฏิทินทันที, การจองของฉันอัปเดต
  - ค้นหาห้องว่างในช่วงเวลาที่ไม่มีใครใช้ → รายการขึ้นครบ
- กรณีพิเศษ:
  - ชนเวลา: create_booking ต้อง fail ด้วยข้อความเหมาะสม
  - ยกเลิก/ปฏิเสธ: ไม่ควรแสดงในปฏิทินรายเดือน
  - กรองบริษัท: เปลี่ยนบริษัทแล้วข้อมูลในปฏิทินและ “การจองของฉัน” เปลี่ยนตาม
  - สิทธิ์: ผู้ใช้ทั่วไปแก้ไข/ยกเลิกรายการของตนเองเท่านั้น
- ความเสถียร:
  - Network error: แสดงข้อความ error และไม่ crash
  - Polling: ไม่ช้า/ไม่หนักเกินไป (10 วินาทีต่อครั้ง)

## 5) เอกสารประกอบและแผนโยกย้ายข้อมูล
- เอกสารการใช้งาน:
  - วิธีจองผ่าน booking_v2: เลือกบริษัท → ค้นหาห้องว่าง → เปิด Modal → บันทึก
  - วิธีดูรายการของฉัน: ขวา → การจองของฉัน
  - วิธีแก้ไข/ยกเลิก: คลิก event ในปฏิทิน → เปิด Modal → บันทึก/ยกเลิก
- เอกสารฝั่งแอดมิน:
  - อนุมัติ/ปฏิเสธ: ผ่านหน้า approve_booking.html
  - รายงาน: monthly_report.html / แท็บ “รายงาน” ใน booking.html
  - update_db.php: ใช้ปรับ schema ให้ครบ (bookings/meeting_rooms)
- แผนโยกย้าย:
  - สำรองฐานข้อมูลเดิม
  - รัน update_db.php ด้วยสิทธิ์ admin เพื่อเพิ่มคอลัมน์ที่ขาด
  - ตรวจสอบค่าบริษัทใน meeting_rooms ให้ถูกต้อง (PTA/PT4/PTE)
  - ทดสอบ booking_v2 ในสภาพแวดล้อมจริง

## 6) Roadmap (ต่อยอด)
- เพิ่ม WebSocket เพื่อ push updates แทน polling
- เพิ่มสิทธิ์ระดับห้อง (requires_approval) ให้บางห้องต้องอนุมัติ
- เพิ่ม export รายงานเป็น Excel/PDF
- เพิ่ม recurring UI ใน v2
